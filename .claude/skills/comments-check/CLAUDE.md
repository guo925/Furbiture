# 代码注释质量检查

从三个维度对 Java 代码进行注释质量检查，输出评分和整改建议。

---

## 参数

```
/comments-check                          → 检查最近修改的 Java 文件
/comments-check <file>                   → 检查指定文件
/comments-check --all                    → 检查 src/main/java 下所有 Java 文件
/comments-check --since <commit>         → 检查指定 commit 以来修改的文件
```

---

## 三大检查维度

### 维度一：注释密度（占比 40 分）

**目标：注释行数 ≥ 代码行数的 30%（即 10 行中约 3 行注释，7 行代码）。**

检查规则：
- 统计每个方法的代码行数（不含空行）和注释行数（`//` 行注释 + `/* */` 块注释 + JavaDoc `/** */`）
- 计算方法级注释覆盖率 = 注释行 / (代码行 + 注释行) × 100%
- 低于 20% → 严重不达标，0 分
- 20%~30% → 基本达标但偏少，15~25 分
- 30%~50% → 达标，25~35 分
- 超过 50% → 可能过度注释，30~40 分（但不超过 40，注释过多也是问题）

重点检查的代码行类型（这些行**必须**有注释）：
- public 方法声明 → 必须有 JavaDoc
- 复杂条件判断（3 个以上条件）→ 必须解释判断意图
- 循环体内的核心操作 → 应说明循环目的
- 调用外部接口/依赖 → 应说明调用目的和预期结果
- 异常处理块 → 应说明异常原因和处理策略
- 魔法数字 → 必须注释说明含义
- Stream/链式调用 → 应分步注释

### 维度二：注释准确性（占比 35 分）

**目标：注释内容必须与代码实际逻辑一致，不能误导读者。**

检查规则：
- 逐行对比注释和代码，检查是否"名实相符"
- 重点检查以下不一致模式：

| 模式 | 示例问题 |
|------|---------|
| 注释说"查询"但代码做了"修改" | `// 查询用户` → 下面调了 `userMapper.update()` |
| 注释里的变量名/方法名已过时 | 重构后注释还是旧名字 |
| 注释描述的条件与代码相反 | `// 如果为空` → 代码是 `if (x != null)` |
| 注释的前提条件代码已不满足 | `// userId 必不为空` → 代码里没有空值检查 |
| 注释的返回值类型/含义与实际不符 | `// 返回用户名` → 实际返回了 User 对象 |
| 注释说"抛出异常"但代码 catch 了 | 异常处理逻辑变更后注释未更新 |

准确性评分：
- 完全一致 → 35 分
- 发现 1~2 处轻微不一致 → 25~30 分
- 发现 3~5 处不一致 → 15~25 分
- 大量不一致（≥6 处或存在严重误导）→ 0~15 分

### 维度三：小白可读性（占比 25 分）

**目标：注释应让刚入行的 Java 开发者也能理解代码意图。**

检查规则：
- 注释是否解释了**为什么这样做**而不只是**做了什么**
- 业务术语是否有解释
- 设计模式/技术名词是否有简要说明
- 复杂算法是否有思路概述

评分细则：

| 检查项 | 分值 | 说明 |
|--------|:--:|------|
| 解释了"Why"而非仅"What" | 0~8 | 好的注释解释设计意图和业务原因 |
| 业务术语有注释或翻译 | 0~5 | 如"SKU（库存量单位）" |
| 技术概念有简要说明 | 0~5 | 如"@Transactional 保证以下操作在同一数据库事务中" |
| 复杂逻辑有流程概述 | 0~5 | 如多步骤业务流程用 1. 2. 3. 列出 |
| 无晦涩缩写 | 0~2 | 变量名和方法名可以有缩写，注释中不应有 |

**参考标准见 `references/standards.md`**，里面有好的注释 vs 不好的注释的对比示例。

## 执行流程

### 第一步：确定检查范围

根据参数确定要检查的文件列表。如果未指定，默认检查当前分支与 main 分支差异中的 Java 源文件：

```bash
git diff main --name-only -- '*.java' ':!*Test*.java' 2>/dev/null | head -20
```

如果没有差异文件，则检查最近修改的前 5 个 Java 源文件：

```bash
find src/main/java -name "*.java" -printf '%T@ %p\n' 2>/dev/null | sort -rn | head -5 | cut -d' ' -f2-
```

### 第二步：逐文件检查

对每个文件，按三维度依次检查。读取完整源码，逐方法分析。

### 第四步：给出修复优先级

将所有问题按严重程度排序：

1. **🔴 严重** — 注释与代码不一致（会误导开发者）→ 立即修复
2. **🟡 重要** — 注释密度严重不足（新人看不懂）→ 尽快补充
3. **🟢 建议** — 可读性可优化 → 下次修改该文件时顺手改

---

## 注意事项

- 只检查 `src/main/java/` 下的业务代码，不检查测试代码
- 不检查 Lombok 自动生成的方法（getter/setter/toString 等）
- 不检查纯接口定义（interface）的方法注释密度（接口方法关注 JavaDoc）
- 对于 `@Override` 方法，如果父类/接口有 JavaDoc，视为已有注释
- 评分是相对的——工具类、简单 CRUD 的标准可以稍低，核心业务逻辑标准从严
